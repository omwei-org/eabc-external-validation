# Execution-Boundary Continuity: Validation Matrix

**Status:** EXPERIMENTAL validation plan; independent end-to-end proof remains a **GAP**.

## Question

Can an independent verifier establish that the authority and evidence evaluated at the execution boundary still govern the actual downstream consequence, despite changing conditions, concurrency, retries, timeouts, and partial failure?

This is narrower than asking whether authorization was valid or whether the gate emitted a commit decision. The validation must link the same governed action across:

```
Governed action
  -> authority and governing-state version
  -> decision / commit record
  -> downstream dispatch
  -> observed effect and target identity
  -> evidence provenance
  -> independent reconstruction
```

## Threat and failure matrix

| Scenario | Required verifier result | Enforcement expectation | Evidence needed | Status |
|---|---|---|---|---|
| Conditions change after authorization but before effect | Reject or report UNKNOWN unless the governing state is revalidated at the effect boundary | Revalidate/version-check as late as the target boundary permits | Authority version, effect-time state/version, ordered timestamps or causal sequence | GAP |
| Stale or replayed authority/evidence | Reject; never bind old evidence to a new action | One-time sequence/nonce and freshness checks bound to the exact action | Replay attempt, rejection record, original and attempted references | GAP |
| Concurrent state change / TOCTOU | Reject or UNKNOWN if the governing-state version changed before effect | Atomic compare-and-commit or target-side fencing; lock-only guarantees must be stated narrowly | Version before decision and at effect, concurrency schedule, final observed state | GAP |
| Sink returns after queue acceptance, before downstream effect | UNKNOWN, not COMMIT | Dispatch acknowledgement must not be treated as effect confirmation | Queue acknowledgement separately from downstream receipt and observed state | Software contract can test this; independent downstream proof is GAP |
| Sink receipt mismatches request, epoch, digest, or confirmation | UNKNOWN, not COMMIT | Validate all receipt fields against the exact governed action | Raw receipt, action digest, authority version, gate decision | Software negative tests exist in an external implementation; independently reproducible evidence not released here |
| Timeout or connection loss after dispatch | UNKNOWN unless downstream state is independently reconciled | Do not retry blindly; use idempotency/fencing and reconcile before retry | Request identity, timeout, downstream status query, observed state | GAP |
| Crash between physical effect and evidence persistence | UNKNOWN until reconciled; never infer no effect from missing evidence | Durable outbox/transactional protocol where possible; target reconciliation otherwise | Crash point, durable records, target state after recovery | GAP |
| Alternate or bypass path to the target | No completeness claim unless all paths are accounted for | Target-side interlock or demonstrated path control | Inventory of effect paths, bypass attempt, target-side enforcement evidence | GAP |
| Receipt issued by a faulty or dishonest adapter | Independent verifier must not mistake adapter assertion for physical truth | Trust boundary and adapter authority must be explicit; independent sensing where consequence warrants it | Adapter identity/provenance plus independent target observation | GAP |

## Minimum acceptance criteria

A validation run should not be called successful unless it:

1. Uses the public execution entry point and records the exact governed action, authority reference, target identity, and governing-state version.
2. Separately records the gate decision, dispatch acknowledgement, downstream receipt, and target-observed effect. These events must not be collapsed into one status.
3. Exercises state change after authorization, replay, concurrency, queue-only dispatch, mismatched receipts, timeout, and crash-after-effect.
4. Uses an observer whose evidence is not merely copied from the gate or generated by the same adapter making the commit claim.
5. Reconstructs the correlation from released evidence alone, including evidence provenance and any clock/ordering assumptions.
6. Reports each case as PASS, FAIL, or UNKNOWN / INCONCLUSIVE with the smallest supported claim. Missing evidence is not proof that execution failed.
7. States which execution paths and target-side bypasses were in scope. A passing adapter test is not hardware atomicity or non-bypassability proof.

## Boundary between evidence and enforcement

Evidence correlation can establish what the released records support. It does not itself prevent a stale authorization from causing an effect. Prevention must be enforced by the execution guard and, where the consequence warrants it, at the target/effect boundary. A downstream receipt is only as trustworthy as its issuer unless independently witnessed.

## Current conclusion

The software-level contract can require an explicit receipt tied to the exact request reference, governing epoch, and action digest, and can refuse to label a missing or mismatched receipt as COMMIT. That is a useful control, but it does **not** independently establish that a physical effect occurred or that the governing conditions remained valid at the moment of effect.

No public, independently reconstructable end-to-end evidence currently accompanies this matrix. Therefore the broader continuity claim remains **GAP / NOT ESTABLISHED**, rather than PASS.

This document is a validation plan and gap statement, not a normative EABC requirement, conformance certificate, or claim of hardware validation.
